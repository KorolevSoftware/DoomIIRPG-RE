# 2026-08-23 — Game flow / state machine investigation

Task: document how the original structures game flow (top-level loop, canvas
states, map lifecycle, worlds, turns, per-frame tick, save hooks) to support a
faithful Phase-5 state-machine skeleton in `new_src/`.

## Hypothesis

The legacy port is a J2ME `Canvas`-centric design: one frame function
(`Canvas::run`) dispatches on an integer `state`, with input dispatched before
the tick and painting after; maps load through a travel-map + two-phase
loading pipeline; turns are driven by explicit `advanceTurn()` calls.

* Read `src/Main.cpp`, `src/App.cpp`, `src/CAppContainer.cpp`,
  `src/Canvas.{h,cpp}`, `src/GameStateRunner.cpp` end-to-end.

## Key extracted facts

1. **Loop**: SDL loop throttled ~15 ms, delta clamped to 125 ms
   (`src/Main.cpp:83-88,133-135`); `DoLoop` adds it to `app->upTimeMs`
   (`src/CAppContainer.cpp:55-61`); `Canvas::run` rolls `app->time` from it
   and advances `gameTime` unless paused/in-menu (`src/Canvas.cpp:745-771`).
   Input → globals (UpdatePlayerVars/gsprite_update/runScriptThreads) run
   every frame regardless of state (`src/Canvas.cpp:781-796`); paint split:
   3D rendered inside `updateView`, overlay in `backPaint`.
2. **States**: 26 `ST_*` values (`src/Canvas.h:68-93`); single mutator
   `Canvas::setState` with old/new hooks and 9 zeroed sub-state vars
   (`src/Canvas.cpp:1020-1217`). Tick dispatcher = if/else chain in `run`
   (`src/Canvas.cpp:805-968`); input dispatcher = `handleEvent`
   (`src/InputEventController.cpp:152-443`). Notably `ST_AUTOMAP` reuses the
   playing input handler. Dead states: `ST_TAF`, vestigial `ST_MIXING`.
3. **Lifecycle**: boot order in `Applet::startup` ends at `setState(ST_LOGO)`
   (`src/App.cpp:128`); LOGO→INTRO_MOVIE→main menu; new game =
   CHARACTER_SELECTION→INTRO pages→`loadMap(1,false,true)`
   (`src/IntroSequenceManager.cpp:131-136`); `loadMap` may brief-save the old
   level then always routes via `ST_TRAVELMAP`; travel map → `ST_LOADING`;
   `loadMedia()` is deliberately **two-phase** (draw bar frame first,
   `src/LoadingManager.cpp:610-616`). Load ordering inside `loadMedia`
   documented step-by-step (header fields incl. `mapSpawnIndex/mapSpawnDir`,
   media manifest registration, entity creation order, `loadWorldState`,
   `spawnPlayer` priority spawnParam > fixed > header, entrance tile event,
   input lockout 200 ms).
4. **Map transition**: not the doors — `EV_CHANGE_MAP` script event sets
   `spawnParam = dir<<10 | tile10`, arms fade flags; fade completion in
   `Render::fadeScene` calls `loadMap` or `saveState(51)`; `ST_SAVING`
   dispatch table routes to travel map/stats menu/quit
   (`src/ScriptThread.cpp:484-517`, `src/Render.cpp:2548-2590`,
   `src/Canvas.cpp:853-903`).
5. **Worlds**: no hub object; narrative ranges Moon 1–3 / Earth 4–6 /
   Hell ≥7 (`src/TravelMapManager.cpp:446-456`) vs sky pairs alternating
   every 5 maps via `skyIndex=((mapID-1)/5%2)*2`
   (`src/LoadingManager.cpp:571-584`); theme media is embedded per map file.
6. **Turns**: `advanceTurn` = player stats tick + bombs + monstersTurn arm +
   monster FX + door auto-close sweep + staticFunc(6) + startRotation
   (`src/Game.cpp:1238-1281`); fires on move-completion, use actions,
   pass-turn, combat end, and deferred after dialogs via `queueAdvanceTurn`
   (`src/DialogSystem.cpp:531`, consumed `src/Canvas.cpp:812-815`).
7. **Playing tick order** fully enumerated (§6 of game-flow.md), including
   that rendering happens *inside* `updateView` before HUD paint.
8. **Saves**: three layers (config / player file / world file), armed through
   `ST_SAVING`/`ST_LOADING` states rather than executed inline.

## Open questions

* `ST_INTER_CAMERA` ("Wolf -> ST_DRIVING" comment, `src/Canvas.h:71`) appears
  tied to a cut driving mechanic; only camera-resume paths remain.
* `saveType` bit meanings beyond {3,43,51} observed values are inferred from
  the dispatch table only.
* `ST_BENCHMARKDONE` has no setter in this port (only input handling);
  likely reachable in original builds via `startSpeedTest(true)` variant.
