## 0. What we are building

The `Menu` soft key opens a full-screen, opaque menu that owns the frame: its
own background, its own bottom panel with a health/shield readout, its own two
soft keys, a scrolling list with a wobbling cursor glyph, its own scrollbar
art, and — through GOTO rows — sub-lists, help text pages and YES/NO confirm
screens.

Data source: **`menus.bin` is parsed** (ADR 0013). Screens absent from that
file (`QUESTLOG` 46, `LOAD` 49, `RESTARTLVL` 52, `SAVEQUIT` 53, all `type 5`
HELP leaves) are built in code by `MenuSession`, mirroring their `initMenu`
cases.

### NEW FACTS found while designing (not in `ui.md` yet)

1. **The menu is opaque; the world is not visible behind it.** `MenuSystem::paint`
   draws `gameMenu_Panel_bottom.bmp` at `(0, 320-64)` and then
   `gameMenu_Background.bmp` (480x320, full screen) at `(0,0)` for every
   `menu >= MENU_INGAME` (`src/MenuSystem.cpp:735-741`; the image is loaded at
   `:126`). `ui.md` §17 lists `imgGameMenuBackground` as unused — it is used.
   (Both BMP sizes verified from the shipped archive.)
2. **The bottom panel carries a health/shield readout**, not HUD widgets
   (`src/MenuSystem.cpp:742-758`), see §7.3.
3. **The original clips the list region with a real clip rect**:
   `graphics->setClipRect(screenRect[0], menuRect[1], screenRect[2], menuRect[3])`
   (`src/MenuSystem.cpp:852`) = **(0, 10, 480, 241)** — note the *width* comes
   from `screenRect`, so the scrollbar (x 430..480) and the info buttons
   (x 376..424) are inside the clip even though they are outside `menuRect`.
   This settles the D1 question: clipping here is **faithful**, so the menu
   uses `Ui::pushClip` (§8.3).
4. **Row background art is drawn at 25 % alpha when idle and 100 % when held.**
   In-game rows get `SetImage(inGame_menu_option_button, false)`,
   `normalRenderMode = 1` (`RENDER_BLEND25`), `highlightRenderMode = 0`
   (`RENDER_NORMAL`) and **no** highlight image
   (`src/MenuSystem.cpp:4458-4466`); `fmButton::Render` therefore re-draws the
   same sheet with the highlight render mode (`src/Button.cpp:178-183`).
   `RENDER_BLEND25` is `glColor4f(1,1,1,0.25)` (`src/GLES.cpp:636-640`) →
   alpha **64**; `RENDER_BLEND50` → **128** (`:642-646`).
   `SetImage(..., center=false)` leaves `centerX/centerY = 0`
   (`src/Button.cpp:67-75`), so the 296x32 art sits at the row's **top-left**
   inside the 296x46 row box.
5. **Touch is suppressed by moving the rect, not the art**: the port's
   `SetTouchArea(x, 350, w, h, false)` for a row with view-relative
   `posY > 210` keeps `touchAreaDrawing` where it was
   (`src/Button.cpp:131-143`, call site `src/MenuSystem.cpp:5099-5102`), i.e.
   the clipped bottom row is **drawn but not clickable**.
6. **A row click is a two-step**: on release the touch handler assigns
   `selectedIndex = button->selectedIndex` and then calls `select()`
   (`src/MenuSystem.cpp:4787-4792`). The left soft key calls `back()`, the
   right one calls `returnToGame()` **directly** (`:4785-4789`) — they are not
   routed through the key-event queue.
7. **`MENUTYPE_VCENTER` (6) does nothing in this port.** `this->type` is only
   ever compared against 5, 7 and 9 (`src/MenuSystem.cpp:405,503,552,1064`,
   `src/GameStateRunner.cpp:216`); nothing centres a type-6 screen
   vertically. A confirm screen is a plain top-aligned list.
8. **Exact scrollbar math** (`fmScrollButton::SetScrollBox`,
   `src/Button.cpp:380-406`; `UpdateContent`, `:456-482`): with
   `V = menuRect[3]` at `initMenu` time, `C = contentPx`, `H = barRect.h`:
   `thumbLen L = V*H/C` (integer), `scrollPx` clamped to `[0, C-V]`,
   `thumbOffset = scrollPx * (H-L) / (C-V)` (the code divides by the cached
   float `(C-V)/(H-L)`).
9. **Wrap-width constants**: `FONT_HEIGHT[0] = 16`, `FONT_WIDTH[0] = 12`,
   `CHAR_SPACING[0] = 11` (`src/App.h:39-41`). The rewrite's font advances 9 px
   (`new_src/text/Font.h:20`) and `Text::getStringWidth` measures 9 px/glyph,
   so **never derive a character budget from a pixel width here** — the
   original's budgets (23 / 30 / 34 / 37 / 49 chars) are computed with 12 and
   11 and are passed as literal character counts (§7.2, §10).
10. **Menu-id → help-resource map** (`src/MenuSystem.cpp:1663-1764`):
    38→1, 39→2, 40→3, 41→7, 43→4, 44→5, 45→6, 59→8, 60→9, 61→10.
11. **`menus.bin` golden values** (decoded from the shipped archive):

## 1. Layering, ownership, threading

```
io/MenuData.{h,cpp}      menus.bin parser (no game knowledge)        [G1]
core/MenuSession.{h,cpp} ALL retained menu state + input + model     [G3+]
ui/MenuModel.h           per-frame view model (POD + borrowed ptrs)  [G3]
ui/MenuView.{h,cpp}      stateless drawMenu(Ui&, const MenuViewModel&) [G3+]
ui/Ui.{h,cpp}            + glyph(), + scrollBarMenu()                [G2]
ui/UiAssets.{h,cpp}      + 10 menu sheets                           [G2]
ui/UiTypes.h             + UiIds, + UiAction::Resume                 [G2]
core/GameStates.h        + StateId::Menu = 1, + Action::MenuResume    [G3]
core/GameContext.{h,cpp} state hooks, tick routing, UI pass, dispatch [G3]
core/PlayerActions.cpp   Action::Menu / BackKey open the menu         [G3]
core/Main.cpp            load menus.bin + text types 2 and 3         [G1]
```

Rules that stay true (checkable):

* `ui/` includes nothing from `domain/game/` or `core/`
  (`grep -rn '#include "domain/game\|#include "core/' new_src/ui/` stays
  empty). `MenuView` never learns about `StateId`, `MenuId` or `Localization`.
* Screen state lives in `MenuSession`, never in `UiState` and never in the
  view (the `LootSession` / `DialogSystem` precedent).
* `MenuSession` owns every `Text` the model points at. Models are stack
  temporaries built once per rendered frame; every pointer inside is borrowed
  and valid for that frame only.
* Single-threaded GL loop: the model build and the view run inside
  `GameContext::render`, between `RenderBackend::beginFrame` and `endFrame`.
* Lifetime: `MenuData` is constructed in `Main.cpp` next to `Tables` and
  outlives `GameContext`; `MenuSession` is a member of `GameContext` like
  `LootSession`.

Build: every group that adds files needs
`cmake -S . -B build_new -DCMAKE_BUILD_TYPE=Debug` (GLOB), then
`cmake --build build_new -j 8`.

## 2. State machine

### 2.1 `StateId::Menu = 1`

Legacy `ST_MENU = 1` (`src/Canvas.h:68`). Add to
`new_src/core/GameStates.h`:

```cpp
Menu = 1,   // legacy ST_MENU (docs/original-code/ui.md §10)
```

### 2.2 Entry

`Action::Menu` **and** `Action::BackKey` open it, from the playing input
handler and therefore **behind the same animation gate as every other playing
action** (`src/PlayingInputHandler.cpp:23-27` early-out;
`:137-158` the two handlers). In `PlayerActions::handleAction`, after the
existing `gateBlocked` return:

```cpp
case Action::Menu:
case Action::BackKey:
    env_.hud->clearMessages();                 // hud->msgCount = 0 (:146,155)
    env_.host->requestState(StateId::Menu);
    break;
```

`GameContext::enterState_(StateId::Menu)`:

```cpp
case StateId::Menu:
    pendingActions_.clear();                   // src/Canvas.cpp:1192-1206
    menu_.begin();                             // initMenu(MENU_INGAME) + startTime latch
    break;
```

`menu_.begin()` = `setMenu(kMenuInGame)` with a cleared nav stack
(`src/MenuSystem.cpp:619-621`) and `selectedIndex = 1`
(`src/MenuSystem.cpp:1549-1573`, §11.1).

### 2.3 Exit

`MenuSession` requests `StateId::Playing` (`returnToGame`,
`src/MenuSystem.cpp:1209-1220`; the `ST_INTER_CAMERA` branch has no rewrite
counterpart yet — see §14). `GameContext::exitState_` for `Menu`: nothing to
undo (the legacy exit hook unpauses the player and clears the menu stack,
`src/Canvas.cpp:1030-1049`; the rewrite has no pause flag and clears the stack
on entry).

Leaving happens on: the right soft key ("Resume"), `back()` with an empty
stack on any of the root-like menus (`src/MenuSystem.cpp:604-607`), and
`ACTION_MENU`/`ACTION_BACK` on the root.

### 2.4 What the menu does to the rest of the frame

| Concern | Behaviour | Citation |
|---|---|---|
| World render | Still rendered, then **completely covered** by the opaque 480x320 background. Do NOT skip `scene_.drawWorld` — nothing establishes that the original stops rendering, and skipping it would change the depth/batch state the next frame relies on. | NEW FACT 1 |
| View weapon | Not drawn: `gameplayView` (Playing/Looting/Dialog) does not include Menu — no code change needed. | `new_src/core/GameContext.cpp:711` |
| Top bar / bottom HUD | Not drawn (`gameplayView` again; legacy skips `hud->draw` while `ST_MENU`). | `src/Canvas.cpp:414-417` |
| Message queue | Emptied on open (`hud->clearMessages()`); `Hud::drawMessages` keeps being called but has nothing to show. | §18, `src/PlayingInputHandler.cpp:146` |
| Cinematic letterbox | Untouched (keyed on `StateId::Camera`). | — |
| Game clock | `gameTime` does not advance in Menu (it advances in Playing/Camera/Looting only) — matches the legacy `app->time = lastTime = upTimeMs` re-stamp on exit. | `new_src/core/GameContext.cpp:167`, `src/MenuSystem.cpp:1211-1212` |
| Lerps / doors / scripts | Not ticked in Menu (they are ticked in Playing/InterCamera/Camera/Dialog). Faithful: `GameStateRunner::menuState` ticks nothing but soft keys. | `src/GameStateRunner.cpp:203-253` |
| Input | Every queued `Action` goes to `MenuSession::handleAction` and nowhere else, exactly like the Dialog and Looting branches. | `src/InputEventController.cpp:314-316` |

`GameContext::tick`, in the per-event loop, next to the Dialog/Looting
branches:

```cpp
if (state_ == StateId::Menu) { menu_.handleAction(a); continue; }
```

The input-block latch (`inputBlocked()`) must **not** gate the menu: the
legacy `ST_MENU` dispatch happens before the blocked-drop check for playing
input, and a script lockout must not freeze an open menu.

### 2.5 Cursor-key repeat

None. `UiInputCollector::onEvent` already drops `ev.key.repeat != 0`
(`new_src/core/UiInputCollector.cpp:50`, port of `src/Input.cpp:740,794`), and
`UiInputCollector::keyAction` is only called for `SDL_KEYDOWN`. Nothing to add;
do not add a repeat timer.

`menu_`, `oldMenu_`, `type_`, `items_[kMaxRows]`, `numItems_`,

### 4.1 `handleAction` (verbatim mapping of `handleMenuEvents`)

| queued `Action` | legacy | effect |
|---|---|---|
| `Forward` | `ACTION_UP` | `scrollUp()` → `moveDir(-1)` |
| `Back` | `ACTION_DOWN` | `scrollDown()` → `moveDir(+1)` |
| `TurnLeft` | `ACTION_LEFT` | `scrollPageUp()` |
| `TurnRight` | `ACTION_RIGHT` | `scrollPageDown()` |
| `Use` | `ACTION_FIRE` | `select(selectedIndex_)` |
| `Menu`, `BackKey` | `ACTION_MENU`, `ACTION_BACK` | `back()` |
| `MenuResume` (NEW) | — (touch-only in the original) | `returnToGame()` |
| `Passturn`, `Automap` | — | ignored (no menu binding) |

`moveDir(n)` — copy the two branches verbatim
(`src/MenuSystem.cpp:401-455`), dropping the `type == 9` (vending) sub-cases:

* types 5 and 7: `scrollIndex_` moves within `[0, numItems_ - kMaxItems)` as
  written (`if (n<0 && scrollIndex>0)` / `else if (n>0 && scrollIndex <
  numItems - maxItems)`), then `selectedIndex_ = scrollIndex_`. **Clamps.**
* every other type: `selectedIndex_ += n` in a `do/while` that skips rows with
  `labelId == 3072` or `flags & (kItemNoSelect|kItemHidden)`, **wrapping**
  through `numItems_-1` / `0`; then the window pull, whose two branches differ
  by sign exactly as written.

`scrollPageUp/Down` = up to `kMaxItems` single `moveDir` steps, undoing the
last one and breaking if the selection wrapped (`:332-363`).

`select(i)`: return early if `items_[i].flags & kItemDisabled` **or**
`disabledByRewrite` (`:2978-2981`); if `type_` is 5 or 7 → `back()`
(`:3004-3011`); else switch on the action — `kActionGoto` →
`gotoMenu(param)`, `kActionBack` → `back()`, everything else per §11.

`back()`: pop `(menu, selectedIndex, scrollIndex)` and re-`initMenu` without
resetting them (the legacy `oldMenu != menu` guard at `:1227-1230` is what
preserves them); with an empty stack call `returnToGame()` when `menu_` is one
of `kMenuInGame`, `kMenuItems`, `kMenuQuestLog` (`:604-607`; the rewrite has no
`MENU_ITEMS_DRINKS` / `MENU_INGAME_SNIPER`).

### 4.2 `initMenu` subset

1. `type_ = menus->type(menuId)` when the id is in the file, else the value
   the code-built case sets.
2. `if (menuId != oldMenu_) { scrollIndex_ = selectedIndex_ = 0; }`
   (`:1227-1230`).
3. Load items: file rows via `MenuData::items`, or the code-built body (§10,
   §11).
4. Per-screen patches. For the root (`:1549-1573`), the ones that survive into
   the rewrite: `selectedIndex_ = 1`; item 2 (`Save Game`) gets
   `kItemDisabled` when `player->inventory[18] == 0`. The camera-active
   variant (items 3/4/5/10 disabled, item 10 retargeted to 58) and the
   `isFamiliar` rebuild are **not** ported (no `isFamiliar`; the camera case is
   unreachable because the menu can only be opened from Playing).
5. Rewrite-only disables (§11.2).
6. If `selectedIndex_ >= numItems_` → `moveDir(-1)`; else if the selected row
   is unselectable → `moveDir(1)` (`:2730-2736`).

## 6. Producer: resolving rows, scroll and the bar

### 6.1 Row composition (per frame, into `MenuSession`-owned buffers)

For each item `i` with `!(flags & kItemHidden)`:

1. `label`: if `flags & kItemChecked`, prefix `'\x87'` + `' '`
   (`:934-938`); append `loc->get(3, index(labelId))`; unless
   `flags & kItemNoDehyphenate`, `dehyphenate()` (`:945-952`).
2. Action rows only: if `getStringWidth() + 10 > itemWidth` →
   `setLength((296 - 10) / 12 == 23)` then append `'\x85'` (`:945-952`).
3. `flags & kItemDivider` → `buildDivider(label, rect.w / CHAR_SPACING[0])`
   = `340 / 11 = 30` cells (`:954-957`). `buildDivider` is not ported yet:
   port it from `src/MenuSystem.cpp` (it fills the buffer with the divider

### 6.3 Scroll pixels from the item index (the honest model)

The original's authoritative model is the item-index pair
`scrollIndex`/`maxItems`; the pixel offset is `[GEC]` (§13, A2). Therefore:

```
scrollPxRaw = sum of itemHeight(j) for non-hidden j in [0, scrollIndex_)
contentPx   = sum of itemHeight(j) for all non-hidden j          (root: 606)
viewPx      = 241      // the region paint() draws (A3, resolved on screen)
scrollPx    = clamp(scrollPxRaw, 0, max(0, contentPx - viewPx))  // root: 0..365
```

`viewPx = 241`, **not** 256 (A3, §14, decided by the user's screen on
2026-08-29): `SetScrollBox` is called from `initMenu`, where `menuRect` is
still `(70,0,340,320-64)` (`src/MenuSystem.cpp:4192`, `:2755-2760`), and
`paint` narrows the rect to 241 afterwards (`:848`), so the reference gives
both numbers. With 256 the clamp stops at 350 and the root's last plate lands
at 210..256 of a 241 px region — its bottom 15 px cut off by the clip, which
is what the user saw. With 241 the clamp stops at 365 and the last plate lands
at 195..241, whole. A touch drag is clamped by the same `viewPx` (§7.6).

### 6.4 The bar

`showBar = contentPx > viewPx` (`:2753`). For the in-game tree
`barRect = (430, menuRect[1] + ((menuRect[3] - 220) >> 1), 50, 220)` evaluated
with the **`initMenu`-time** rect → **(430, 18, 50, 220)** (§13).
**The producer computes the thumb, the primitive only draws it.** One
formula, one place: `MenuSession::buildViewModel` fills

```
barThumbLen    = viewPx * barRect.h / contentPx           // root: 241*220/606 = 87
barThumbOffset = (contentPx - viewPx) == 0 ? 0
               : scrollPx * (barRect.h - barThumbLen) / (contentPx - viewPx)
```

citing NEW FACT 8, and `Ui::scrollBarMenu(barRect, thumbOffset, thumbLen)`
(§8.2) blits the four sheets. (The dialog/loot `Ui::scrollBar` keeps its math
inside the primitive because that widget has no producer state; here the
producer already owns `scrollPx`, `contentPx` and `viewPx`, so splitting the
formula across the boundary would duplicate them.)

### 7.6 Drag scrolling (added 2026-08-29, G4b) — FAITHFUL

The original scrolls the menu by dragging, and §7.4's earlier "the only
continuous scroll is a drag on the bar" was **wrong**:

* **List content.** `MenuSystem::handleUserMoved` — while a touch is down and
  the current point is inside the scroll widget's `boxRect`, it calls
  `SetContentTouchOffset` and latches `field_0x38_`
  (`src/MenuSystem.cpp:4894-4897`); every later move runs
  `UpdateContent`, i.e. `scroll = latchedScroll + (latchedY - y)` clamped to
  `[0, contentPx - viewPx]` (`src/Button.cpp:456-478`, `:443-452`). 1:1 in
  pixels, vertical only.
* **Bar.** A press inside `barRect` sets `field_0x54_ = 0` and calls
  `fmScrollButton::Update` (`:4691-4699`, `isMainMenuScrollBar == false` for
  the in-game tree, `:4175`), which centres the thumb on the touch, clamps it
  to the track and maps it back to the content offset through
  `field_0x50_ = (C - V) / (H - L)` (`src/Button.cpp:497-534`).
* **No activation from a drag.** `handleUserTouch(b == false)` clears whichever
  latch is set and **returns** before reaching the button hit test
  (`:4676-4689`); the move handler also clears every button highlight on the
  frame the drag starts (`:4855-4870`).
* **Threshold.** The port ignores moves inside a 6x6 box around the press point
  (`[GEC]`, `:4842-4847`, `src/TouchController.cpp:127-131`). The rewrite
  applies it symmetrically: **more than 3 px on either axis** promotes the
  press to a drag; anything smaller stays a click and still activates the row.
  This is the one number here that is port code rather than J2ME original.
* **No kinetics.** The original has none either — releasing stops the list.

Rewrite mapping (all state in `MenuSession`, none in `UiState` or the view):
`MenuSession::updateDrag(const UiInput&)` runs from `GameContext::render`
*before* `buildViewModel`; a drag writes `dragScrollPx_` (the widget's
`field_0x44_`) which `scrollPixels()` returns instead of the index-derived
offset, and `moveDir()` drops it again — the original does the same, since its
`[GEC]` sync block rewrites `field_0x44_` from the item model at the end of
every key move (`:463-546`), so A2's index model stays the authority for keys.
The view learns only `MenuViewModel::rowHits`, and `Ui::clearActive()` drops
the latched plate.

  is always flush with y = 10 (our model says yes; a pixel-scrolling original
  might not).

## 16. DEVIATION — deliberate departures from `src/`

Each item states what the port does, what the rewrite does instead, and why.
None of these is a bug; do not "restore" the verbatim code.

* **D1 — text-page scroll bound (types 5 and 7), added 2026-08-29 (G6 fix).**
  `moveDir`'s down bound for the cursor-less branch is
  `scrollIndex < numItems - maxItems` (`src/MenuSystem.cpp:401-455`), i.e. an
  ITEM count with the `[GEC]` constant `maxItems = 4` (`:1231`). The rewrite
  maps a type 5/7 scroll index to pixels through §6.3/A2 and clamps to
  `contentPx - kViewPx`, so the last ~4-10 indices all map to the same clamped
  offset: Down keeps counting with no visual change and the user must press Up
  exactly that many times before the page moves again.
  **Rewrite:** the bound becomes `scrollIndex < maxScrollIndex()`, the FIRST
  index whose pixel offset already reaches the clamp
  (`new_src/core/MenuSession.cpp`, `MenuSession::maxScrollIndex()` and the
  type 5/7 branch of `moveDir`). No dead range remains, one line per press.
  **Why not the port's own type 5/7 pixel mapping** (`selectedIndex * itemH`
  clamped, `src/MenuSystem.cpp:502-507`): it still leaves ~9 dead presses and
  additionally makes the visible step uneven (6-14 px).
  This is a **product decision, not a fidelity one**: both the `maxItems` bound
  and the type 5/7 pixel mapping are `[GEC]` port-era code, so there is no J2ME
  behaviour to be faithful to. Scoped to the type 5/7 branch only — types 1/6
  keep the legacy window pull untouched, and types 5/7 have no action rows, so
  selection and `ListRow` are unaffected. All four scroll inputs (Down/Up, the
  wheel — which queues the same `Action::Back`/`Forward` — the page drag and the
  bar drag, both of which clamp to `contentPx - kViewPx`) now reach exactly the
  same bottom.
