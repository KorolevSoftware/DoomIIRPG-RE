# Use inventory items (items menu → confirm → `Player::useItem`), status effects, buff HUD — spec

Date: 2026-10-28. ADR: [0032](../adr/0032-item-use-ownership.md).
Facts (do not re-derive, cite these):
- `docs/original-code/loot-inventory.md` §8 "Using items" (raw: `docs/research/2026-10-28-use-item.md`)
- `docs/original-code/ui.md` §17a "Items menu and use confirm" (raw: `docs/research/2026-10-28-items-menu.md`)
- Base designs: `specs/2026-08-28-menu.md`, ADR 0013 (menus from `menus.bin`), ADR 0028 (monster
  attacks run on `Combat` inside `ST_PLAYING`; `combat.active` == legacy `ST_COMBAT`).

## 0. Decisions (summary; rationale in ADR 0032)

1. `Player` owns the item switch (`useItem`), the effect planes (`statusEffects[54]`, `buffs[30]`)
   and their helpers, like the legacy `Player` (`src/Player.cpp:801-959`, `:1448-1595`).
2. `Player` has no `Game`. `useItem` returns a tri-state `UseResult`; the **caller** (MenuSession,
   the only legacy caller, `src/MenuSystem.cpp:3149-3151`) calls `game->advanceTurn()` when it is
   `Used`. Ordering is unchanged: in legacy `advanceTurn` is the last statement of `useItem`
   (`src/Player.cpp:956-958`), after the sound and the decrement.
3. `Player` gets a `Hud*` + `const Localization*` (setter, like `setDefs`) so `addHealth` can emit
   common string 111 exactly where legacy does (`src/Player.cpp:445-449`). Side effect, intended
   and faithful: the food pickup (`new_src/domain/game/ItemPickup.cpp:88`, legacy
   `src/Entity.cpp:204`) now also shows "Gained N health".
4. "Monster turn inside the menu": the rewrite has no `ST_COMBAT`; `Combat::performMonsterAttack`
   only sets `combat.active = true` (`new_src/domain/game/Combat.cpp:223`). MenuSession therefore
   treats `combat.active` after the snap as "the canvas left ST_MENU" and calls `returnToGame()`
   (requests `Playing`), where `tickPlaying` runs the attack (`new_src/core/GameContext.cpp:440-449`).
   Not a deviation in behaviour: legacy leaves the menu for combat at the same point
   (`src/Combat.cpp:165`, `src/MenuSystem.cpp:3158-3160`).

Golden frames: the capture window has no input, so nothing is opened/used — every golden frame
must stay byte-identical after each group. G3 draws only when `numbuffs != 0`, which is 0 at boot.

### Monster turn inside the menu — what happens (verify on screen)
`useItem` → `Game::advanceTurn` arms `monstersTurn = 1` and runs doors + `SCR_PER_TURN`
(`new_src/domain/game/Game.cpp:324-340`) **while in Menu**; `snapMonsters(true)`
(`new_src/domain/game/MonsterSystem.cpp:285-322`) runs `monsterAI()`, snaps every monster step,
and if an attacker is queued calls `performMonsterAttack` → `combat.active` → menu closes →
`tickPlaying` plays the attack (`new_src/core/GameContext.cpp:440-449`). With no attacker,
`monstersTurn` stays 1 with `monstersUpdated = true`; back in Playing `updateMonsters` closes the
turn (`MonsterSystem.cpp:253-265`) — same as legacy. A second use inside the same menu visit arms a
fresh turn (`monstersUpdated = false` in advanceTurn), as in legacy.
Known residual difference (deviation **U2**): door auto-close started by advanceTurn runs on
`DoorSystem`'s own animation, which `snap(-1)` does not touch (legacy doors are lerp sprites and
snap shut). The door finishes closing after Resume. Logged nowhere; acceptable.
