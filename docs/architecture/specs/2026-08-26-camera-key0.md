# Cinematic camera key-0 fix — restore legacy tri-state startup

**Date:** 2026-08-26 · **Status:** approved for implementation · **Scope:** delta-spec on
`specs/2026-08-24-intro-sequence.md` (cinematics §) · **Root cause report:**
`docs/research/2026-08-26-cinematic-jerk.md` (RC#1 primary, RC#2 secondary, RC#3 deferred)

## 0. Problem in one paragraph

Legacy arms a cinematic with `activeCameraKey = -1` (`src/ScriptThread.cpp:188`) plus a
separate boolean `activeCameraView = true` (`:186`; together they form
`isCameraActive()`, `src/Game.cpp:3297-3299`). While the key index is −1 the ST_CAMERA
tick **skips** `Update` (`src/Canvas.cpp:949-952`) and the renderer draws whatever pose
fields hold — exactly the static key-0 values `setupCamera` wrote with −2 channels
resolved against the player (`src/ScriptThread.cpp:198-227`), drawn every frame by
`MayaCamera::Render` reading `x/y/z/pitch/yaw/roll` directly
(`src/MayaCamera.cpp:302-310`, FOV 315 / 290 under dialog). The script's first
`EV_ADV_CAMERAKEY` then calls `NextKey()` which does `activeCameraTime = gameTime;
activeCameraKey++` (`src/ScriptThread.cpp:690-697`, `src/MayaCamera.cpp:36-44`) — landing
on **key 0**, which plays its full authored duration. The rewrite initializes
`activeCameraKey_ = 0` (`new_src/core/GameContext.cpp:583`) and `nextKey()`
unconditionally increments (`:599`), so key 0 never plays: cam7 opens with a hard cut to
key1's fixed yaw (the jerk) and runs 1500 ms of its 2750 ms; cam10 (all-shot-is-key0,
500 ms + ms=0 tail) completes in the tick it starts and never renders; boot cams lose
their openers (cam0 −999 ms, cam5 −1999 ms, cam1 −1499 ms).

## 1. Chosen mechanism — two-field model (legacy-exact)

Split the overloaded sentinel. Keep `activeCameraKey_` with its pure legacy meaning and
re-introduce the binding flag legacy carries alongside it:

```cpp
// GameContext.h (private section, replaces the comment at :178)
bool cameraView_ = false;            // legacy activeCameraView (src/ScriptThread.cpp:186);
                                     // cleared by Snap tail (src/MayaCamera.cpp:379)
int  activeCameraKey_ = -1;          // legacy activeCameraKey: -1 = bound-not-started
```

Public probe changes meaning from "key started" to "cinematic bound" — the exact
`isCameraActive` analog:

```cpp
// GameContext.h:108
bool cameraActive() const { return cameraView_ && cameraCamIdx_ >= 0; }
    // src/Game.cpp:3297-3299 (activeCameraView && activeCamera != nullptr)
```

Why this shape and not the alternatives:

- *Keep single field, arm at `activeCameraKey_ = -1`:* rejected — every `>= 0` gate that
  doubles as "is a cinematic running" breaks silently in ~8 places (§2 matrix would all
  need case-by-case edits anyway), and "no cinematic" vs "armed" become
  indistinguishable, so `render()` cannot pick the maya pose for the opener frame.
- *Add an enum phase machine (`Armed/Playing/Done`):* rejected — over-modeled; legacy
  demonstrably runs two orthogonal bits and every consumer maps onto one or the other.
  Converging on the original removes guesswork about which consumer sees which phase.

No ADR: the model is a restoration of the original's, not a novel design.

### Phase table (normative)

| Phase | `cameraView_` | `activeCameraKey_` | Render shows | `tickCinematicClock` |
|---|---|---|---|---|
| Idle | `false` | −1 | player view | returns early |
| **Armed** (post-STARTCINEMATIC, pre-first-ADV) | `true` | **−1** | **static resolved key-0 pose** left by `maya_.setup()` (incl. −2 inherit), FOV 315 | returns early (Update gated off in legacy too, `src/Canvas.cpp:950`) |
| Playing | `true` | 0 … numKeys−1, or ≥ numKeys when parked past last | interpolated / snap-held maya pose | full boundary engine (unchanged) |
| Finished/skipped | `false` | −1 | player view | returns early |

Note the armed phase can last arbitrarily long (cam5 has a 1–3 s WAIT500 + walk-lerp
lead-in between `STARTCINEMATIC`@2422 and the first `ADV_CAMERAKEY`@2517, map00 disasm);
during it legacy renders the frozen key-0 pose — that is precisely the seamless opener
for cam7/cam10 whose key0 yaw is the −2 player-inherit sentinel.

### Q1 verification — first rendered frame (asked explicitly)

Yes, legacy renders a **static key-0 pose** between STARTCINEMATIC and the first ADV:
`setupCamera` writes key 0's six channels into the camera object with −2 resolved from
the captured player pose and xyz `<<4` (`src/ScriptThread.cpp:198-227`); the ST_CAMERA
tick skips `Update` while `activeCameraKey == -1` (`src/Canvas.cpp:950`); `MayaCamera::
Render` draws those fields directly (`src/MayaCamera.cpp:302-310`). `MayaCamera::Update`
initial behavior is irrelevant in that window because it is never called; once key 0
starts (first ADV → `NextKey`), `resetTweenBase(keyOffset+0)` re-resolves the same key as
tween base (`src/MayaCamera.cpp:43`). The rewrite equivalent already exists:
`maya_.setup()` resolves key 0 into `m_pose` (`new_src/core/MayaCamera.cpp:38-47`) — the
armed-phase render simply must stop being gated away from it (§2 row R1).

## 3. Exact edits (one group)

Files touched: `new_src/core/GameContext.h`, `new_src/core/GameContext.cpp`.
No new files ⇒ **no CMake reconfigure needed** (GLOB picks up nothing new).

1. **GameContext.h**
   - :108 replace probe body (H1).
   - :177-184 member block: add `bool cameraView_ = false;`, update the
     "doubles as activity flag" comment to describe the two-field model + phase table
     of §1.
2. **GameContext.cpp — startCinematic (:571-588)**
   - Capture from **dest** fields like legacy (`src/ScriptThread.cpp:192-196`):
     `pose.x = p.destX; pose.y = p.destY; pose.z = p.destZ; pose.yaw = p.destAngle & 0x3FF;`
     (pitch stays absent; viewPitch has no cinematic counterpart yet). Equal to view
     fields in every current flow (triggers fire from `finishMovement` after arrival),
     but faithful when a future script starts a camera mid-walk.
   - Replace `activeCameraKey_ = 0;` with `cameraView_ = true; activeCameraKey_ = -1;`
     (W1). `cameraStartTime_ = gameTime`, `cinUnpauseTime_`, `skipCinematic_ = false`
     stay as-is (legacy stamps `activeCameraTime` here too, `src/ScriptThread.cpp:191`).
   - Guard the state swap like legacy: only `setState(StateId::Camera)` when
     `state != StateId::Camera` (`src/ScriptThread.cpp:406-408`) — a chained
     STARTCINEMATIC must not re-clear subtitles/pending input via the enter hook.
3. **GameContext.cpp — tickCinematicClock (:644-646)** guard becomes (T1):
   ```cpp
   if (!cameraView_ || activeCameraKey_ < 0 || cameraCamIdx_ < 0 ||
       cameraCamIdx_ >= (int)sys_.map->mayaCameras.size()) return;
   ```
4. **GameContext.cpp** mechanical swaps: :45 (S1), :199 (V1), :345 (T2), :371+377 (D1),
   :721 (W2), :735 (W3), :929 (R1), :942 (R2 prefix).
5. **finishCinematic (:714-726)** — append the RC#2 micro-fix (see §4).
6. TEMP log (remove with the group): keep the existing `[script] STARTCINEMATIC` line;
   add after `:599` in `nextKey()`:
   `std::fprintf(stderr, "[cam] nextKey idx=%d elapsed=%ld\n", activeCameraKey_, (long)(gameTime - cameraStartTime_));`
   — acceptance probe P1 below reads it; delete once accepted.

### RC#2 included (trivial, independent): snap-tail view reset

At the end of `finishCinematic()` (after `setState(Playing)`, before
`flushParkedThreads(false)`), port the Snap-tail reset (`src/MayaCamera.cpp:396-397`):

```cpp
sys_.player->viewPitch = 0;                 // viewPitch = destPitch = 0 (:396)
if (sys_.player->viewAngle == sys_.player->destAngle)
    sys_.player->startRotation();           // startRotation(true) step-vector refresh (:397)
```

Cost ≈3 lines, no new state, zero visible behavior today (rewrite `viewPitch` is only
written by loot sessions, which cannot overlap a cinematic; `startRotation()` snaps
`viewAngle = destAngle` and recomputes step vectors, `new_src/domain/game/Player.cpp:13-27`
— with the equality guard it cannot fabricate a turn, so no spurious
`finishRotationFired` FACE event). Do NOT call it unguarded: an unsettled angle means a
scripted rotation is in flight and arrival handling owns the refresh.

### DEFERRED — do not implement in this group

- **RC#3 shake flat envelope** (`new_src/ui/Hud.cpp:163-173` →

  key-0 fix, but the envelope lives in code shared by gameplay shakes and needs its own
  visual A/B pass against the imp attack + boot intro. Separate spec/group.
- Skip fast-forward fidelity (legacy expires the *camera thread's* WAITs via

  have no consumer yet).

## 4. Groups & acceptance criteria

**GROUP 1 (only group):** all edits above. No threading concerns (single GL loop).
Data ownership unchanged (`maya_` still owned by `GameContext`; `cameraView_` lifecycle
bounded by startCinematic ↔ finish/skip).

Log probes (stderr, build_new/new_src):

- **P1 key0 lands:** boot replay must print `[script] STARTCINEMATIC camera=0` followed
  by `[cam] nextKey idx=0` (today: `idx=1`). Same for cam5, cam7, cam10.
- **P2 durations:** cam7 span `STARTCINEMATIC camera=7` → `FINISH` ≈ **2750 ms**
  (today 1500); cam10 > 0 (today 0, finishes same tick); boot total grows by ≈1 s (cam0)
  / ≈2 s (cam5).
- **P3 no regression:** ESC-skip still ends any cinematic promptly (skip latch
  `GameContext.cpp:167` untouched); opening a dialog during a cinematic still freezes
  the camera clock (`gameTime` freeze, `GameContext.cpp:127-128` + S1 redirect).

User-eyes checklist (each item: what you should SEE):

1. **Boot intro** plays its opening shots again — cam0 and cam5 each hold their first
   high establishing shot noticeably longer (~1 s / ~2 s added); overall intro pacing no
   longer feels hurried.
2. **Sergeant cutaway (cam7):** after the squad dialog, the camera **glides smoothly
   from your own facing** (no sideways jerk at the cut) across the room for ~1.25 s,
   then pans right ~1 s, then settles on the elevator-door viewpoint and holds ~0.5 s —
   roughly twice as long as before, no speed-up feel.
3. **Doorway cutaway (cam10):** stepping out of the elevator bay through the doorway
   shows a brief (~0.5 s) side view of the scientist/Klingon pantomime — previously a
   barely-visible flash/nothing.
4. After every cinematic the view returns to the normal player camera without a hitch
   (RC#2 guard: nothing observable unless a future pitched state exists).
5. ESC during any cinematic skips to gameplay as before; letting a dialog pop during a
   cinematic freezes the world until dismissed, then the cinematic continues.

Verify with: `cmake --build build_new -j 8`, run
`build_new/new_src/DoomIIRPG`, watch boot intro, walk out of the elevator area
((9,19) sergeant trigger → cam7; (10,19) doorway → cam10), capture stderr for P1/P2.
