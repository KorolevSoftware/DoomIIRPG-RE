# Форматы ресурсов Doom II RPG — техническое описание

Документ описывает форматы бинарных файлов игры Doom II RPG (мобильная версия, J2ME/iPhone)
и объясняет, как они были реконструированы по исходному коду C++.

---

## Источник знаний: исходный код

Все форматы восстановлены **не угадыванием**, а прямым чтением декомпилированного
исходного кода игры:

| Файл | Что содержит |
|---|---|
| `src/Render.cpp` | `FinalizeMedia()` — загрузка палитр и тексел; `beginLoadMap()` — парсинг карты |
| `src/GLES.cpp` | `CreateTextureForMediaID()` — декодирование спрайтов и текстур |
| `src/TinyGL.cpp` | Матричная математика, координатная система |
| `src/Enums.h` | Константы `TILENUM_*` — имена всех тайлов |
| `src/Resource.h` | Имена файлов ресурсов |

Методология:
1. Читаем C++ функцию загрузки (например `FinalizeMedia`)
2. По переменным и смещениям определяем формат байтов
3. Воспроизводим в Python с теми же именами переменных что в C++ (n12, m, n14…)
4. Запускаем, смотрим результат, корректируем

## Файл newMappings.bin

Главный индексный файл. Содержит метаданные обо всех медиа-ресурсах игры.
Размер фиксированный — **18 432 байта**.

### Структура (последовательно)

```
512 × int16   mediaMappings     — тайл N → диапазон медиа-ID [mapping[N], mapping[N+1])
1024 × uint8  mediaDimensions   — packed log2: биты [7:4] = log2(ширина), [3:0] = log2(высота)
4096 × int16  mediaBounds       — 4 int16 на медиа-ID: shapeMin, shapeMax, minY, maxY (uint8)
1024 × int32  mediaPalColors    — цвет палитры / флаг ссылки
1024 × int32  mediaTexelSizes   — размер тексел / флаг ссылки
```

### Как читать тайл

```python
tile_id = 276  # TILENUM_DOOR_UNLOCKED
lo = mediaMappings[tile_id]       # первый медиа-ID
hi = mediaMappings[tile_id + 1]   # следующий (исключительно)
# медиа-ID для этого тайла: range(lo, hi)
# несколько медиа-ID = анимационные кадры
```

### mediaDimensions

```
byte = mediaDimensions[media_id]
log_w = (byte >> 4) & 0xF    # log2(ширина)
log_h =  byte       & 0xF    # log2(высота)
width  = 1 << log_w          # всегда степень двойки
height = 1 << log_h
```

Типичные значения: `0x88` → 256×256, `0x87` → 256×128, `0x44` → 16×16.

### mediaPalColors и mediaTexelSizes — флаги

Оба поля используют одинаковую схему флагов:

```
Бит 31 = MEDIA_FLAG_REFERENCE (0x80000000)
  → этот медиа-ID — ссылка на другой
  → биты [9:0] содержат медиа-ID источника
  → данных в файле нет, нужно взять у источника

Бит 31 = 0
  → биты [29:0] = количество элементов (для палитры) или size-1 (для тексел)
```

## Файл newPalettes.bin

Содержит палитры (таблицы цветов) для всех медиа-ресурсов.

### Формат

Записи идут **последовательно** для всех медиа-ID от 0 до 1023, пропуская ссылки:

```
для каждого media_id где (mediaPalColors[id] & 0x80000000) == 0:
    N × uint16   RGB565 цвета  (N = mediaPalColors[id] & 0x3FFFFFFF)
    4 байта      маркер CAFEBABE
```

Всегда N = 256 (полная палитра 8-bit индексирования).

### Конвертация RGB565 → RGBA8888

Формат RGB565: 5 бит красного, 6 бит зелёного, 5 бит синего, упакованы в 16-bit:

```
[15:11] = R5   [10:5] = G6   [4:0] = B5

r8 = (r5 << 3) | (r5 >> 2)   # 5 бит → 8 бит (масштаб с округлением)
g8 = (g6 << 2) | (g6 >> 4)   # 6 бит → 8 бит
b8 = (b5 << 3) | (b5 >> 2)   # 5 бит → 8 бит
a8 = 255
```

### Цветовой ключ прозрачности

Пиксели с цветом маджента считаются прозрачными (alpha = 0):

```
if r8 >= 250 and g8 == 0 and b8 >= 250:  alpha = 0  # #FF00FF
if r8 >= 250 and g8 == 4 and b8 >= 250:  alpha = 0  # вариант для аракнотрона
```

Эта же проверка есть в `GLES.cpp::CreateTextureForMediaID`.

## Файлы newTexels000.bin … newTexels038.bin

Содержат сырые данные тексел (пиксельные индексы в палитру).

### Разбивка на файлы

Данные разбиты на файлы по **262 144 байта** (0x40000). Граница определяется
накопленным смещением (`n12` в C++ коде `FinalizeMedia`):

```python
n12 = 0   # позиция в текущем файле
m   = 0   # индекс файла (newTexels{m:03d}.bin)

для каждого media_id (не ссылка):
    читаем n14 байт по смещению n12
    пропускаем 4 байта маркера
    n12 += n14 + 4

    if n12 > 0x40000:
        m  += 1    # переходим к следующему файлу
        n12 = 0    # позиция сбрасывается
```

Ссылочные медиа-ID (бит 31 = 1) полностью пропускаются — у них нет данных в файле.

### Вычисление n14

```python
raw_val = mediaTexelSizes[media_id] & 0xFFFFFFFF
n14 = (raw_val & 0x3FFFFFFF) + 1   # +1 потому что хранится size-1
```

## Декодирование текстур

### Определение типа: стена или спрайт

```python
size = len(texel_bytes)      # n14 из выше
area = width * height

if size == area:
    # Стена / пол: сырые индексы, row-major
else:
    # Спрайт: колонковое RLE сжатие
```

### Стеновые текстуры

Простейший формат: `size` байт, каждый — индекс в палитру, построчно слева-направо:

```python
for i, idx in enumerate(texel_bytes):
    x = i % width
    y = i // width
    pixel[y][x] = palette[idx]
```

### Спрайты — колонковое RLE

Используется в GLES.cpp строки 946–1031. Схема хранения:

```
[пиксельные индексы ... | ниббл-секция | пары запусков | 2 байта счётчика]
```

**Разметка буфера:**

```
Size        = len(raw)
last2       = (raw[Size-1] << 8) | raw[Size-2]   # размер (ниббл + пары)
nybble_start = Size - last2 - 2                   # начало ниббл-секции

num_cols     = shapeMax - shapeMin                # количество колонок
nybble_bytes = (num_cols + 1) >> 1               # ceil(num_cols / 2)
run_pair_start = nybble_start + nybble_bytes      # начало пар (y, высота)
```

**Ниббл-секция** — по 4 бита на колонку, packed low-first:

```python
col_offset 0 → нижний ниббл байта 0
col_offset 1 → верхний ниббл байта 0
col_offset 2 → нижний ниббл байта 1
...
```

Значение нибблa = количество запусков для этой колонки.

**Пары запусков:** для каждого запуска:
```
y_start    uint8   — строка начала
run_height uint8   — количество строк
```

**Пиксели:** читаются последовательно с начала буфера (`pixel_idx = 0`),
заполняя запуски в порядке обхода колонок.

**Алгоритм декодирования:**

```python
pixel_idx = 0
run_ptr   = run_pair_start

for col_offset in range(num_cols):
    col       = shapeMin + col_offset
    run_count = nybble_at(col_offset)

    for _ in range(run_count):
        y_start    = raw[run_ptr];     run_ptr += 1
        run_height = raw[run_ptr];     run_ptr += 1

        for row in range(y_start, y_start + run_height):
            output[row * width + col] = raw[pixel_idx]
            pixel_idx += 1
```

## Файлы карт map00.bin … map09.bin

Бинарные BSP-карты. Функция загрузки: `Render::beginLoadMap` в `Render.cpp`.

### Общая структура

```
Заголовок карты       (размеры, счётчики)
Секция тайловой сетки (тайловые данные сетки)
Секция сущностей      (монстры, объекты, триггеры)
BSP-узлы              (дерево с геометрией)
Maya-камеры           (пути камер для катсцен)
```

Между секциями — 4-байтные маркеры `CAFEBABE` или `DEADBEEF`.

### Координатная система

Внутри игры используется fixed-point математика. Вершины хранятся как `uint8`:

```
vertex_world = byte_value * 128   (сдвиг <<7)
tile_index   = world_coord >> 6   (1 тайл = 64 world-unit)
```

Перевод в OBJ (float, Y-up правая система):

```python
WORLD_SCALE = 1.0 / 64.0   # 1 OBJ unit = 1 тайл

def to_obj_coords(x, y, z):
    return x * WORLD_SCALE, z * WORLD_SCALE, -y * WORLD_SCALE
```

Ось Z инвертируется потому что в игре Y направлена вглубь экрана,
а в OBJ стандарте — Z направлена на зрителя.

### BSP-дерево и полигоны

BSP-дерево содержит как внутренние узлы (разделители пространства),
так и листья с реальной геометрией. Ключевое открытие:

```
nodeOffsets[n] == 0xFFFF  →  листовой узел, содержит полигоны
nodeOffsets[n] != 0xFFFF  →  внутренний узел, содержит ссылки на детей
```

Если читать внутренние узлы как геометрию — получается мусор.
Фильтрация по этому условию убирает ~99% лишних данных.

### Формат nodePolys (геометрия листа)

```
1 байт    meshCount         — количество мешей
для каждого меша:
    4 байта  unknown
    uint16   packed         — (textureID << 7) | polyCount
для каждого полигона:
    uint8    vertCount
    vertCount × (uint8 x, uint8 y, uint8 z)
```

### Порядок обхода вершин и сторонность

Игра рендерит **по часовой стрелке** (CW) как лицевую сторону
(culling = CCW задних граней). OBJ-формат ожидает **против часовой** (CCW).

Решение — реверсировать порядок вершин при экспорте:

```python
face_str = "f " + " ".join(f"{vi}/{ti}" for vi, ti in reversed(idxs))
```

## Итог: как читать ресурсы по шагам

```
1. newMappings.bin
   → получаем: для каждого тайла — диапазон медиа-ID,
                для каждого медиа-ID — размер, ссылки, bounds

2. newPalettes.bin
   → читаем последовательно все не-ссылочные медиа-ID
   → каждая запись: N×uint16 RGB565 + CAFEBABE
   → конвертируем в RGBA8888 LUT (256 элементов)

3. newTexels000-038.bin
   → читаем последовательно, переключаем файл когда n12 > 0x40000
   → каждая запись: n14 байт + CAFEBABE
   → если size == width*height: стена (raw индексы)
   → иначе: спрайт (RLE декодер)

4. Применяем LUT: texel_byte → palette[texel_byte] → RGBA пиксель
```
